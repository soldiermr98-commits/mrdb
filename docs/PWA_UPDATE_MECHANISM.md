# مکانیزم به‌روزرسانی خودکار PWA — زنجیرهٔ کامل از سرور تا گوشی کاربر

> **خلاصه:** از نسخهٔ PWA 1.5.4 / افزونه 1.7.2 به بعد، وب‌اپ خودش نسخهٔ سرور را چک می‌کند و با انتشار نسخهٔ جدید، کاربران (حتی اپ‌های نصب‌شده روی گوشی) با بنر مرئی «نسخهٔ جدید آماده است» و کلیک روی «بروزرسانی» آپدیت می‌شوند. این سند مرجع کامل این مکانیزم، رفع اشکال و آیین انتشار نسخه است.
> **آخرین به‌روزرسانی:** ۱۶ اکتبر ۲۰۲۶ — موج v1.5.6 / افزونه 1.7.5 (فیکس حادثهٔ CORS «Pragma» + بازگشت UX بنر مرئی)

---

## ۱) زنجیرهٔ آپدیت — چهار لایهٔ دفاعی

هر کاربر (تب مرورگر یا اپ نصب‌شده) با این چهار لایه همیشه به آخرین نسخه می‌رسد:

```text
┌─────────────────────────────────────────────────────────────────────┐
│ لایه ۱ — SW autoUpdate (از v1.5.1)                                  │
│  مرورگر هنگام ناوبری sw.js را چک می‌کند؛ نسخهٔ جدید → skipWaiting    │
│  + clientsClaim → کلاینت خودکار کنترل را می‌گیرد و reload می‌شود.     │
├─────────────────────────────────────────────────────────────────────┤
│ لایه ۲ — چکر نسخهٔ اپ (v1.5.4 ← v1.5.5 semver ← v1.5.6 بنر مرئی)    │
│  هر ۲ دقیقه + روی بازگشت به تب: GET /version?_=timestamp            │
│  نسخهٔ سرور «جدیدتر»؟ → بنر «نسخهٔ جدید آماده است» با دکمهٔ          │
│  «بروزرسانی» (UpdateReadyBanner) — کلیک کاربر = reload کش‌باست‌شده    │
│  (فقط جدیدتر — سرورِ قدیمی‌تر هرگز اعلان نمی‌سازد)                    │
├─────────────────────────────────────────────────────────────────────┤
│ لایه ۳ — هش محتوا (از v1.5.4)                                       │
│  تغییر content_hash (ذخیرهٔ هر چیزی در پیشخوان) → رویداد             │
│  content-changed → همهٔ ویوها داده‌ها را بدون reload refetch می‌کنند  │
├─────────────────────────────────────────────────────────────────────┤
│ لایه ۴ — صفحهٔ #/debug (هوشمندانهٔ دستی — آخرین پناه)                 │
│  پاک‌سازی کامل SW + کش‌ها + localStorage + بارگذاری مجدد              │
│  فقط برای کلاینت‌های ≤1.5.3 که چکر نسخه ندارند                       │
└─────────────────────────────────────────────────────────────────────┘
```

### نقش سرور — اندپوینت `GET /version`

سبک، عمومی، بدون احراز هویت، ضدکش (LiteSpeed nocache رسمی از 1.7.3 + cache-busting کلاینت):

```json
{
  "pwa_version": "1.5.6",        // نسخه‌ای که کلاینت «باید» داشته باشد — از فیلد پیشخوان
  "plugin_version": "1.7.5",
  "db_version": "1.4.0",
  "server_time": "2026-10-16 00:20:35",
  "timestamp": 1792097435,
  "content_hash": "S8Yc3j74pidG_1792096721"  // با هر ذخیرهٔ پیشخوان عوض می‌شود
}
```

- **pwa_version** از گزینهٔ `mrdastbaaf_pwa_version` خوانده می‌شود — از افزونهٔ 1.7.4 در پیشخوان (تنظیمات ← «نسخه و به‌روزرسانی PWA») قابل ویرایش است و fallback کهنهٔ `1.5.3` حذف شده است.
- **content_hash** با ذخیرهٔ هر گزینهٔ `mrdastbaaf_*` یا پست ووکامرسی خودکار عوض می‌شود؛ کلاینت‌ها فقط داده‌ها را refetch می‌کنند (بدون reload).

## ۲) آیین انتشار نسخهٔ جدید (برای کارفرما — ۳ قدم)

1. **مستقر کردن باندل:** ZIP `mrdastbaaf-pwa-build-vX.Y.Z.zip` مرکز دانلود را در ریشهٔ `app.mrdastbaaf.com` استخراج کنید.
2. **اعلام نسخه:** پیشخوان ← مستر دستباف ← تنظیمات ← کارت «نسخه و به‌روزرسانی PWA» ← «نسخهٔ مستقر PWA» را به همان عدد تغییر دهید.
3. **ذخیره.** همین ذخیره هش محتوا را هم تازه می‌کند.

**نتیجه:** همهٔ کلاینت‌های 1.5.6+ (تب و اپ نصب‌شده، اندروید/iOS) حداکثر تا ۲ دقیقه بعد (یا اولین بازگشت به اپ) **بنر «نسخهٔ جدید آماده است»** را می‌بینند؛ با کلیک روی «بروزرسانی» به نسخهٔ جدید می‌روند — همان UX سادهٔ نسخه‌های اولیهٔ محصول. کاربر می‌تواند نسخهٔ خودش را در `#/debug` ببیند. دکمهٔ «بعداً» فقط برای همان نسخهٔ سرور تا آخر سشن بنر را مخفی می‌کند.

> ⚠️ اگر عدد را تغییر ندهید، اتفاقی نمی‌افتد (هیچ حلقه‌ای شکل نمی‌گیرد — فیکس 1.5.5)؛ کاربران فقط با لایهٔ ۱ (SW autoUpdate) دیرتر یا با ناوبری بعدی آپدیت می‌شوند. این «fail-safe» عمدی است.

## ۳) وضعیت کلاینت‌های قدیمی (یک‌بار برای همیشه)

| باندل کاربر | چکر نسخه؟ | آپدیت خودکار | اقدام دستی |
|---|---|---|---|
| 1.5.6 به بعد | ✅ فیکس کامل + بنر مرئی | ✅ کامل | هیچ |
| 1.5.4 و 1.5.5 | ❌ فچِ چکر قربانی باگ CORS «Pragma» بود | نیمه — فقط لایهٔ ۱ (SW) با ناوبری بعدی | هیچ — آپدیت به 1.5.6 خودکار از مسیر SW |
| 1.5.1 تا 1.5.3 | ❌ | نیمه — فقط لایهٔ ۱ (SW) در ناوبری‌های بعدی | توصیه‌شده: یک‌بار `#/debug` ← «پاک‌سازی کامل و بارگذاری مجدد» |
| ≤1.5.0 | ❌ (SW حالت prompt) | ❌ | الزامی: یک‌بار `#/debug` |

**پیام رسمی به کاربران چسبیده (فقط یک‌بار):** «یک بار به آدرس app.mrdastbaaf.com/#/debug بروید و دکمهٔ "پاک‌سازی کامل و بارگذاری مجدد" را بزنید.» از آن به بعد همهٔ آپدها خودکار است.

## ۴) رفع اشکال — خطاهای «ارتباط با سرور برقرار نشد» و خالی‌بودن دوره‌ها/پلن‌ها

### ۴-۱) حادثهٔ CORS «Pragma» — ریشهٔ قطعی (۱۶ اکتبر ۲۰۲۶ / فیکس 1.5.6/1.7.5)

**علامت:** حتی در incognito دوره‌ها و پلن‌ها لود نمی‌شدند («پلنی برای نمایش وجود ندارد»)، ورود پیامکی «ارتباط با سرور برقرار نشد» می‌داد، پرداخت هم درگیر بود؛ curl همه‌چیز را سالم جواب می‌گرفت.

**ریشه:** PWA از v1.5.4 هدر `Pragma: no-cache` را به همهٔ درخواست‌ها اضافه کرده بود؛ Pragma جزو CORS-safelisted headers مرورگر نیست و در فهرست `Access-Control-Allow-Headers` افزونه هم نبود → پاسخ preflight رد می‌شد → **تمام** فچ‌های مرورگر با `TypeError: Failed to fetch` شکست می‌خوردند. سرور کاملاً سالم بود. بازتولید کنترل‌شده در مرورگر: درخواست با `Accept`+`Cache-Control` → 200 OK؛ فقط با افزودن `Pragma` → `TypeError: Failed to fetch`.

**فیکس دوطرفه (1.5.6/1.7.5):** (۱) حذف Pragma از کلاینت (apiClient + فچ چکر نسخه) — کش‌باستینگ `?_=timestamp` و `Cache-Control` کافی است؛ (۲) در افزونه: Pragma به فهرست مجاز اضافه شد + هر هدر آینده‌ای که مرورگر در preflight بخواهد به‌طور امن (توکن‌های `[A-Za-z0-9-]`) به پاسخ اضافه می‌شود — این کلاس از باگ‌ها دیگر قابل تکرار نیست. تست قرارداد «Pragma هرگز ارسال نشود» هم اضافه شد.

**اثر جانبی مهم:** فچِ چکر نسخه هم قربانی همین باگ بود → مکانیزم push نسخه از 1.5.4 تا 1.7.4 عملاً به کلاینت‌ها نمی‌رسید (به همین دلیل کاربر هیچ‌وقت اعلان آپدیت نمی‌دید). از 1.5.6 چکر سالم است و بنر مرئی کار می‌کند.

### ۴-۲) حادثهٔ حلقهٔ reload (۱۵ اکتبر ۲۰۲۶ / فیکس 1.5.5/1.7.4)

**علامت:** در اپ نصب‌شده، موقع ورود با پیامک، پیام «ارتباط با سرور برقرار نشد؛ اتصال اینترنت خود را بررسی کنید» + خطاهای بارگذاری پراکنده؛ در incognito سالم.

**ریشه (نه اینترنت، نه سرور):** حلقهٔ reload چکر نسخهٔ v1.5.4 — سرور به‌خاطر fallback کهنه `1.5.3` نسخهٔ «قدیمی‌تر» اعلام می‌کرد و چکر با مقایسهٔ `!==` صفحه را بی‌نهایت reload می‌کرد؛ reload وسط درخواست `verify-otp` آن را abort می‌کرد و apiClient همان پیام اتصال را نشان می‌داد. (بعدها مشخص شد بخش عمدهٔ علامت‌ها از حادثهٔ ۴-۱ بود — دو باگ مستقل با علائم مشابه.)

**درس‌های ماندگار (پیاده‌سازی‌شده در 1.5.5/1.7.4):**
1. مقایسهٔ نسخه فقط جهت «جدیدتر» — سرور قدیمی‌تر/نامعتبر = بی‌عمل (utils/versionCompare + تست‌های اختصاصی).
2. گزینهٔ نسخه فیلد پیشخوانی دارد — دیگر هیچ‌وقت نیازی به SQL دستی نیست.
3. SQL دستی روی `wp_options` ممنوع؛ اگر اتفاق افتاد، روتین ارتقای 1.7.4 ردیف تکراری را خودکار پاک می‌کند (فقط قدیمی‌ترین ردیف می‌ماند).

**اگر دوباره دیدید:** نسخهٔ اعلامی سرور را با `curl "https://mrdastbaaf.com/wp-json/mrdastbaaf/v1/version"` چک کنید — اگر با باندل مستقر فرق دارد، فیلد پیشخوان را اصلاح کنید. روی دستگاه مشکل‌دار هم یک‌بار `#/debug`.

## ۵) نکات فنی تکمیلی

- **WebAPK اندروید:** آیکون/نام لانچر با آپدیت PWA تازه نمی‌شود (کروم باید WebAPK را re-mint کند — ممکن است تا چند روز طول بکشد)؛ کد و رابط کاربری تازه می‌شود. نام‌گذاری آیکون‌ها از v1.2.7 برای ترغیب re-mint تنظیم شده است.
- **کش LiteSpeed:** پاسخ REST با API رسمی `litespeed_control_set_nocache` (1.7.3) + هدرهای no-store + cache-busting کلاینت، سه‌لایه ضدکش است؛ GET کلاینت هم `?_=timestamp` دارد.
- **نکتهٔ iOS:** در حالت standalone سافاری گاهی SW را سخت‌گیرانه‌تر نگه می‌دارد؛ لایهٔ ۲ (چکر نسخه) این را جبران می‌کند چون مستقل از SW با `location.href` کش‌باست‌شده کار می‌کند.
- **تست مکانیزم:** بعد از استقرار، در `#/debug` نسخهٔ باندل را ببینید؛ عدد پیشخوان را یکی بالا ببرید و ذخیره کنید — تا ۲ دقیقه (یا با اولین سوییچ به اپ) بنر «نسخهٔ جدید آماده است» باید ظاهر شود؛ با کلیک «بروزرسانی» صفحه به نسخهٔ جدید می‌رود؛ سپس عدد را به مقدار واقعی برگردانید.
