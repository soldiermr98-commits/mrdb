# مکانیزم به‌روزرسانی خودکار PWA — زنجیرهٔ کامل از سرور تا گوشی کاربر

> **خلاصه:** از نسخهٔ PWA 1.5.4 / افزونه 1.7.2 به بعد، وب‌اپ خودش نسخهٔ سرور را چک می‌کند و با انتشار نسخهٔ جدید، کاربران (حتی اپ‌های نصب‌شده روی گوشی) بدون هیچ کاری آپدیت می‌شوند. این سند مرجع کامل این مکانیزم، رفع اشکال و آیین انتشار نسخه است.
> **آخرین به‌روزرسانی:** ۱۵ اکتبر ۲۰۲۶ — موج v1.5.5 / افزونه 1.7.4 (فیکس حلقهٔ reload + فیلد پیشخوان)

---

## ۱) زنجیرهٔ آپدیت — چهار لایهٔ دفاعی

هر کاربر (تب مرورگر یا اپ نصب‌شده) با این چهار لایه همیشه به آخرین نسخه می‌رسد:

```text
┌─────────────────────────────────────────────────────────────────────┐
│ لایه ۱ — SW autoUpdate (از v1.5.1)                                  │
│  مرورگر هنگام ناوبری sw.js را چک می‌کند؛ نسخهٔ جدید → skipWaiting    │
│  + clientsClaim → کلاینت خودکار کنترل را می‌گیرد و reload می‌شود.     │
├─────────────────────────────────────────────────────────────────────┤
│ لایه ۲ — چکر نسخهٔ اپ (از v1.5.4، فیکس‌شده در v1.5.5)                │
│  هر ۲ دقیقه + روی بازگشت به تب: GET /version?_=timestamp            │
│  نسخهٔ سرور «جدیدتر» از باندل؟ → force reload با cache-busting      │
│  (فقط جدیدتر — سرورِ قدیمی‌تر هرگز reload نمی‌سازد)                   │
├─────────────────────────────────────────────────────────────────────┤
│ لایه ۳ — هش محتوا (از v1.5.4)                                       │
│  تغییر content_hash (ذخیرهٔ هر چیزی در پیشخوان) → رویداد             │
│  content-changed → همهٔ ویوها داده‌ها را بدون reload refetch می‌کنند  │
├─────────────────────────────────────────────────────────────────────┤
│ لایه ۴ — صفحهٔ #/debug (هوشمندانهٔ دستی — آخرین پناه)                 │
│  پاک‌سازی کامل SW + کش‌ها + localStorage + بارگذاری مجدد              │
│  فقط برای کلاینت‌های ≤1.5.3 که چکر نسخه ندارند                       │
└─────────────────────────────────────────────────────────────────────┘
```

### نقش سرور — اندپوینت `GET /version`

سبک، عمومی، بدون احراز هویت، ضدکش (LiteSpeed nocache رسمی از 1.7.3 + cache-busting کلاینت):

```json
{
  "pwa_version": "1.5.5",        // نسخه‌ای که کلاینت «باید» داشته باشد — از فیلد پیشخوان
  "plugin_version": "1.7.4",
  "db_version": "1.4.0",
  "server_time": "2026-10-15 19:18:07",
  "timestamp": 1792079287,
  "content_hash": "JjQme8zlBEdl_1792074674"  // با هر ذخیرهٔ پیشخوان عوض می‌شود
}
```

- **pwa_version** از گزینهٔ `mrdastbaaf_pwa_version` خوانده می‌شود — از افزونهٔ 1.7.4 در پیشخوان (تنظیمات ← «نسخه و به‌روزرسانی PWA») قابل ویرایش است و fallback کهنهٔ `1.5.3` حذف شده است.
- **content_hash** با ذخیرهٔ هر گزینهٔ `mrdastbaaf_*` یا پست ووکامرسی خودکار عوض می‌شود؛ کلاینت‌ها فقط داده‌ها را refetch می‌کنند (بدون reload).

## ۲) آیین انتشار نسخهٔ جدید (برای کارفرما — ۳ قدم)

1. **مستقر کردن باندل:** ZIP `mrdastbaaf-pwa-build-vX.Y.Z.zip` مرکز دانلود را در ریشهٔ `app.mrdastbaaf.com` استخراج کنید.
2. **اعلام نسخه:** پیشخوان ← مستر دستباف ← تنظیمات ← کارت «نسخه و به‌روزرسانی PWA» ← «نسخهٔ مستقر PWA» را به همان عدد تغییر دهید.
3. **ذخیره.** همین ذخیره هش محتوا را هم تازه می‌کند.

**نتیجه:** همهٔ کلاینت‌های 1.5.4+ (تب و اپ نصب‌شده، اندروید/iOS) حداکثر تا ۲ دقیقه بعد (یا اولین بازگشت به اپ) خودکار به نسخهٔ جدید می‌روند. کاربر می‌تواند نسخهٔ خودش را در `#/debug` ببیند.

> ⚠️ اگر عدد را تغییر ندهید، اتفاقی نمی‌افتد (هیچ حلقه‌ای شکل نمی‌گیرد — فیکس 1.5.5)؛ کاربران فقط با لایهٔ ۱ (SW autoUpdate) دیرتر یا با ناوبری بعدی آپدیت می‌شوند. این «fail-safe» عمدی است.

---

## ۳) وضعیت کلاینت‌های قدیمی (یک‌بار برای همیشه)

| باندل کاربر | چکر نسخه؟ | آپدیت خودکار | اقدام دستی |
|---|---|---|---|
| 1.5.5 به بعد | ✅ فیکس‌شده (semver) | ✅ کامل | هیچ |
| 1.5.4 | ✅ اما با باگ `!==` | ✅ (با اولین آپدیت به 1.5.5 فیکس می‌شود) | هیچ |
| 1.5.1 تا 1.5.3 | ❌ | نیمه — فقط لایهٔ ۱ (SW) در ناوبری‌های بعدی | توصیه‌شده: یک‌بار `#/debug` ← «پاک‌سازی کامل و بارگذاری مجدد» |
| ≤1.5.0 | ❌ (SW حالت prompt) | ❌ | الزامی: یک‌بار `#/debug` |

**پیام رسمی به کاربران چسبیده (فقط یک‌بار):** «یک بار به آدرس app.mrdastbaaf.com/#/debug بروید و دکمهٔ "پاک‌سازی کامل و بارگذاری مجدد" را بزنید.» از آن به بعد همهٔ آپدها خودکار است.

## ۴) رفع اشکال — خطای «ارتباط با سرور برقرار نشد» در ورود پیامکی (۱۵ اکتبر ۲۰۲۶)

**علامت:** در اپ نصب‌شده، موقع ورود با پیامک، پیام «ارتباط با سرور برقرار نشد؛ اتصال اینترنت خود را بررسی کنید» + خطاهای بارگذاری پراکنده؛ در incognito سالم.

**ریشه (نه اینترنت، نه سرور):** حلقهٔ reload چکر نسخهٔ v1.5.4 — سرور به‌خاطر fallback کهنه `1.5.3` نسخهٔ «قدیمی‌تر» اعلام می‌کرد و چکر با مقایسهٔ `!==` صفحه را بی‌نهایت reload می‌کرد؛ reload وسط درخواست `verify-otp` آن را abort می‌کرد و apiClient همان پیام اتصال را نشان می‌داد.

**درس‌های ماندگار (پیاده‌سازی‌شده در 1.5.5/1.7.4):**
1. مقایسهٔ نسخه فقط جهت «جدیدتر» — سرور قدیمی‌تر/نامعتبر = بی‌عمل (utils/versionCompare + ۹ تست).
2. گارد ضدحلقهٔ sessionStorage (حداکثر یک reload برای هر نسخه در ۹۰ ثانیه).
3. گزینهٔ نسخه فیلد پیشخوانی دارد — دیگر هیچ‌وقت نیازی به SQL دستی نیست.
4. SQL دستی روی `wp_options` ممنوع؛ اگر اتفاق افتاد، روتین ارتقای 1.7.4 ردیف تکراری را خودکار پاک می‌کند (فقط قدیمی‌ترین ردیف می‌ماند).

**اگر دوباره دیدید:** نسخهٔ اعلامی سرور را با `curl "https://mrdastbaaf.com/wp-json/mrdastbaaf/v1/version"` چک کنید — اگر با باندل مستقر فرق دارد، فیلد پیشخوان را اصلاح کنید. روی دستگاه مشکل‌دار هم یک‌بار `#/debug`.

## ۵) نکات فنی تکمیلی

- **WebAPK اندروید:** آیکون/نام لانچر با آپدیت PWA تازه نمی‌شود (کروم باید WebAPK را re-mint کند — ممکن است تا چند روز طول بکشد)؛ کد و رابط کاربری تازه می‌شود. نام‌گذاری آیکون‌ها از v1.2.7 برای ترغیب re-mint تنظیم شده است.
- **کش LiteSpeed:** پاسخ REST با API رسمی `litespeed_control_set_nocache` (1.7.3) + هدرهای no-store + cache-busting کلاینت، سه‌لایه ضدکش است؛ GET کلاینت هم `?_=timestamp` دارد.
- **نکتهٔ iOS:** در حالت standalone سافاری گاهی SW را سخت‌گیرانه‌تر نگه می‌دارد؛ لایهٔ ۲ (چکر نسخه) این را جبران می‌کند چون مستقل از SW، با `location.href` cache-bust شده کار می‌کند.
- **تست مکانیزم:** بعد از استقرار، در `#/debug` نسخهٔ باندل را ببینید؛ عدد پیشخوان را یکی بالا ببرید و ذخیره کنید — اپ باید تا ۲ دقیقه (یا با اولین سوییچ به اپ) خودکار reload شود؛ سپس عدد را به مقدار واقعی برگردانید.
